# Правила поиска и отбора мотосалонов

Обновлено 20.11.2026 по решению Максима. Настройка: `data/lead-search-settings.json`.
Эти правила применяются к будущим проверкам и новой строгой выборке. Старые карточки
и историческая станция не получили подтверждение автоматически.

## Обязательные условия

1. Проверить компанию и филиал по названию, городу, адресу и опубликованным контактам.
2. Дополнительно проверить поле сайта в Яндекс Картах, 2ГИС и Google Картах.
   Карточки не обязаны существовать на всех трёх площадках, но результат поиска
   каждой должен быть задокументирован. Открыть подходящую карточку, раскрыть
   контакты и ссылку сайта; поисковый сниппет не является проверкой.
3. Найти прямой рабочий Telegram администратора или владельца, опубликованный
   в конкретной карточке этого бизнеса хотя бы на одной из трёх площадок.
   Сохранить точную ссылку, источник и подтверждение роли. Если роль не указана
   и независимо не подтверждена в свидетельстве, не назначать её по догадке.
4. Канал, бот, общий номер, `t.me/+номер`, приглашение, аккаунт, угаданный по
   username/номеру, или Telegram только с сайта/VK не заменяют обязательную ссылку
   в карточке на картах. Сниппет и совпадение названия также недостаточны.
5. Если карта/поле сайта недоступны, данные конфликтуют или принадлежность контакта
   не подтверждена — отложить кандидата. Не заполнять пробел правдоподобным значением.

`not_found_in_checked_sources` означает только «ссылка не найдена в проверенных
источниках». Это не утверждение «у бизнеса нет сайта». Найденный сайт открывают
и сверяют с бизнесом; отдельно проверяют другие уже известные официальные источники,
не скрывая расхождения. Из старого `has_website: false` вывод об отсутствии не делается.

## Где хранить доказательства

Исследователь дополняет только назначенные `data/facts/<slug>.json`:

- `sources`: существующий массив `{id, url, checked_at, excerpt, evidence_path}`.
  `id` уникален; обязательны URL, дата и хотя бы выписка либо локальное доказательство.
- `lead_search_checks.maps`: объект с ключами `yandex_maps`, `two_gis`, `google_maps`.
- Для каждой площадки: `status`, `url`, `checked_at`, `identity_status`,
  `identity_evidence`, `source_id`, `website`.
- `status: verified` — открыта именно карточка нужного бизнеса;
  `identity_status: verified`, в `identity_evidence` записаны совпавшие признаки.
  Нужен канонический URL конкретной организации, не общей выдачи и не короткая
  ссылка перенаправления. Для `two_gis` — `/firm/…`, для Яндекса — `/maps/org/…`,
  для Google — `/maps/place/…` либо ссылка конкретного места с `cid`/place ID.
- `status: missing` — поиск выполнен, подходящая карточка не найдена;
  `identity_status: not_found`, `url` содержит реальный поисковый запрос по
  названию, городу и адресу, а свидетельство описывает проверенный результат.
  Это не отсутствие бизнеса и не отсутствие сайта.
- `inaccessible`/`conflicting` — честно записать причину, не заменять на `missing`.
- `website: {status, value, note}`: `found` и точный URL сайта, либо
  `not_found_in_checked_sources` и `value: null`; `note` описывает проверку.
  `unknown`, `inaccessible`, `conflicting` блокируют готовность.
- `source_id` ссылается на `sources` с точно тем же URL карточки/поиска и свидетельством.

`lead_search_checks.telegram`:

```text
status: verified | missing | inaccessible | conflicting
url: точный https://t.me/<username> прямого рабочего чата либо null
kind: direct_chat (channel/bot не проходят отбор)
role: administrator | owner (неизвестная роль не проходит отбор)
role_evidence: короткая выписка, подтверждающая роль и связь контакта с бизнесом
platform: yandex_maps | two_gis | google_maps
source_id: ID той же verified-карточки из maps и sources
checked_at: ISO 8601 с часовым поясом
```

Проверяющий сверяет фактическое содержание карточек с этой записью. Валидатор
контролирует структуру и согласованность доказательств, но не доказывает правдивость
самой выписки. Если исходная карточка не прочитана, нельзя ставить `verified`.

## Проверка и будущая выгрузка

Без сети и записи файлов:

```powershell
node scripts/find-owners.js --all --dry-run
node scripts/find-owners.js --slugs <slug> --dry-run
```

После реальной проверки назначенных кандидатов:

```powershell
node scripts/find-owners.js --all
node scripts/find-owners.js --only-no-site --limit 25
node scripts/find-owners.js --only-with-site --limit 25
```

`--only-no-site` означает «ссылка сайта не найдена в проверенных карточках», а не
«сайта нет в интернете». `--only-with-site` требует найденную ссылку. Неизвестный
результат не проходит ни один из этих фильтров. Лимит применяется к готовым записям.

Результаты будущего запуска: отдельные `sales/qualified_owners_telegram.json` и
`.csv`. JSON включает комплект использованных доказательств. Частичный запуск
обновляет выбранные готовые записи и сохраняет остальные ранее прошедшие строгую
проверку записи; сохранённые доказательства также проверяются на соответствие
текущим правилам. Если они не подходят — запись файлов останавливается с ошибкой.
Пустая готовая выборка ничего не создаёт и не перезаписывает. Нет подходящих
доказательств — значит нужна проверка, а не что у бизнеса отсутствует сайт/Telegram.

Исторические `owners_telegram.json`, `.csv`, `.vcf`, факты, станция и статусы
переписок остаются отдельными; они не являются новой строгой выборкой.
Импорт телефонов и старые эвристики из прежнего скрипта больше не вызываются
его `main()`. Программа не открывает карты за исследователя и не отправляет сообщения.

Технические проверки: `node scripts/test-lead-search-policy.js`. Они используют
только синтетические записи и виртуальную файловую систему; это не аудит бизнеса.
